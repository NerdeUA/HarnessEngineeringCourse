# Звіт ЛР7 — OpenTelemetry, MLflow і Phoenix

Дата: 2026-10-02. Середовище: кластер ABox Kubernetes, kagent 0.x, один OTLP Collector і три бекенди трейсів.

## Виконано

- Розгорнуто Jaeger 2.21.0, MLflow 3.11.1 та OpenTelemetry Collector contrib 0.161.0 у namespace `lab7`.
- Налаштовано один приймач OTLP/gRPC і три призначення: Jaeger OTLP/gRPC, Phoenix OTLP/HTTP, MLflow OTLP/HTTP.
- Для Phoenix налаштовано API key з Kubernetes Secret; для MLflow — experiment ID `0`.
- Тимчасово увімкнено OTLP-трейсинг kagent і явно вимкнено збір чутливого вмісту; згодом Flux повернув tracing у вимкнений стан, оскільки зміна джерела лишилась незакоміченою.
- Надіслано A2A-запит до `retrieval-agent`; trace ID `644cf78a6f9aa2973256730a078d7832` виявлено в кожному бекенді.

## Порівняння

| Рішення | Що показало під час запуску | Сильна сторона для GenAI | Виявлене обмеження |
|---|---|---|---|
| OpenTelemetry + Collector (інструментація/транспорт) | Єдиний OTLP-вхід і fan-out до трьох призначень | Відкриті, незалежні від бекенду домовленості; централізована маршрутизація й обробка | OTel сам по собі не є UI для аналізу чи довготривалим сховищем трейсів |
| Jaeger 2 | За trace ID отримано три span-и: A2A POST контролера, `invoke_agent` та POST retrieval-agent | Наочна наскрізна часова шкала сервісного трейсингу; корисна загальна базова лінія | У демо дані лише в пам'яті; немає GenAI evaluation workflow; у трейсі не було дочірнього span-а моделі/інструмента |
| MLflow Tracing | Пошук experiment `0` повернув вісім трейсів за вікно запиту, включно з тим самим ID; стани повернутих записів — `OK` | Поєднує GenAI-трейси з експериментами й процесами оцінювання | Потрібно організовувати дані за експериментами; поточний SQLite-сетап має один worker |
| Phoenix | Запит до проєкту `default` повернув той самий trace ID із трьома span-ами | Спеціалізований інтерфейс для LLM-трейсів, проєктів і GenAI-аналізу | Для OTLP потрібна API-key автентифікація; побачені тут span-и були сервісними, без семантики LLM |

## Спостереження й обмеження

Однаковий trace ID у трьох сховищах підтверджує роботу fan-out через OTel і приймання даних бекендами. Це корисна перевірка сумісності, але вона сама по собі не оцінює якість відповіді моделі. kagent CLI не зміг декодувати JSON-RPC-відповідь: поле `error.data` мало форму об'єкта, хоча CLI очікував типізований масив. Endpoint контролера повернув HTTP 200 і породив span-и, але ці докази не встановлюють, що агент успішно відповів. Трейс складався лише з трьох сервісних/агентських span-ів, без дочірніх span-ів моделі чи інструментів. Чутливий вміст було навмисно вимкнено, тому промпти й відповіді у трейси не потрапляли.

Спочатку Phoenix вимагав коректну автентифікацію system key, а MLflow — явний allowlist хостів, включно з варіантами host:port. Після виправлення цих налаштувань Collector і всі бекенди перейшли в Ready, а трейс з'явився в усіх системах. Трейс отримано під час live-вікна з увімкненим tracing. Після перевірки Flux відновлено; наступна синхронізація повернула `OTEL_TRACING_ENABLED=false`, бо зміну ABox HelmRelease навмисно не комічено. Отже, бекенди й докази реальні, але tracing наразі не є постійним/увімкненим у синхронізованому джерелі ABox. Репозиторій курсу містить values snippet та інструкції; для постійного режиму потрібно внести snippet у GitOps-джерело й опублікувати його. Коміту в ABox не було.

## Висновок

Ці продукти працюють на різних рівнях, а не є прямими замінниками: OTel стандартизує інструментацію і транспорт, Jaeger надає загальну часову шкалу трейсів, MLflow пов'язує трейси з експериментами/оцінюванням, а Phoenix фокусується на аналізі LLM-трейсів. Для лабораторної fan-out через OTel Collector дав змогу порівняти бекенди на тих самих даних. Перед реальною оцінкою потрібно виправити декодування A2A-відповіді у CLI, підтвердити успішний запуск агента з інструментом, а також визначити політику збереження, retention і редагування даних.

## Повторна перевірка — 2026-10-03

Deployment-и Jaeger, MLflow та OTel Collector лишалися Ready; Pod-и Phoenix і PostgreSQL були Running. Kustomization `releases` у Flux лишалася нездоровою, оскільки HelmRelease Phoenix перебуває у Stalled після попереднього таймауту встановлення. Новий read-only A2A-запит `message/stream` до `k8s-agent` дійшов до контролера, але агент повернув OpenAI `401 invalid_api_key`; успішної відповіді агента не отримано. ModelConfig посилається на Secret `kagent/kagent-openai`, ключ `OPENAI_API_KEY`; його значення не читалося й не записувалося. Раніше зафіксований спільний trace лишається доказом fan-out між бекендами, але повторна перевірка не підтверджує новий наскрізний trace або успішний виклик агента. Потрібно поза Git замінити цей Secret, повторити безпечне завдання й зіставити його trace у трьох бекендах. Публікація курсового артефакту, перемикання джерела й постійний tracing очікують підтвердження доступу до пакета.

Після зчитувальних перевірок StatefulSet і Deployment Phoenix були Ready. Далі точковий Flux reset/reconcile лише `HelmRelease/phoenix` завершився успішно (`UpgradeSucceeded`); Kustomization `releases` повернулася до `Ready=True` і `Healthy=True` на upstream артефакті `0.9.5`. Spec HelmRelease і OCI-джерело не змінювалися. Це усуває попередній блокер здоров'я Phoenix, але не виправляє OpenAI-ключ і не завершує міграцію курсового артефакту.

Після ротації ключа користувачем прямий A2A-запит `message/stream` завершився успішно. `k8s-agent` викликав read-only інструмент `k8s_get_resources` для Node і повернув `abox-control-plane`, `abox-worker` та `abox-worker2` — усі у стані `Ready`. У чинному kagent HelmRelease досі немає `otel` values, тому успішний виклик не є доказом нового trace; перед порівнянням цього виклику в Jaeger, MLflow і Phoenix необхідно опублікувати та синхронізувати курсовий реліз.

## Фінальне перемикання на курсовий артефакт — 2026-10-03

Приватний курсовий артефакт `0.1.2` перевірено через read-only Secret `flux-system/ghcr-pull`, і тепер це активне джерело. Обидві release Kustomization мають стан Ready на revision `0.1.2@sha256:843f72154cc59d2435ff8a90912a8f36f99bf91fab0e1a7d2e5b64f702cacb2b`. У kagent увімкнено OTLP/gRPC tracing із вимкненим збором чутливого вмісту. Ротація Neo4j credential і перевірка входу після Helm upgrade успішні; реліз використовує `neo4j/neo4j-password`, а Neo4j MCP імпортує `kagent/neo4j-auth`.

Новий безпечний A2A-запит після перемикання дістався `k8s-agent`, але завдання завершилося OpenAI `401 invalid_api_key`. У маскованій помилці було `OPENAI_A**_KEY`; це може свідчити, що фактичний credential досі є placeholder, однак Kubernetes Secret не переглядався. Jaeger записав помилковий trace `cb7d9f9a5bbd019bb90cbe603ac99481` із model/agent span-ами у стані error. Його ще не зіставлено в MLflow і Phoenix; це не доказ успішного завдання. Останній крок лабораторної 7 — поза Git оновити OpenAI Secret і зіставити успішний trace після перемикання у всіх трьох бекендах.
